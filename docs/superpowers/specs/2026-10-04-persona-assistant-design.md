# 人设助手 设计

日期：2026-10-04 · 状态：待用户审阅

## 目标

主播只会用几句话形容 AI 的性格，不了解（也不该了解）接话、静默、心里话、输出协议这些工作流。人设助手把主播的随口描述整理成一份简短克制的人设，并把 AI 的名字/别名、AI 对主播的称呼写进对应字段。所有工作流规则由程序负责，永远不进人设。

## 背景

2026-10-02 的直播日志显示：人设里写了「仅输出【PASS】」「全角括号心里话」「正常输出」等格式要求，与程序追加的 v2 协议冲突，模型多次按人设格式输出，被协议解析器丢弃，AI 表现为该说话时不说。那份人设由开发者编写；普通主播不会写这些，但也写不出一份好用的人设。

## 已确认的决定

| 项 | 决定 |
|---|---|
| 交互方式 | 主播先随便写，助手只追问缺的关键信息，再生成（方案 3） |
| 字段联动 | 问到的名字写入 `live.wakeKeywords`，称呼写入 `live.selfName`，人设正文同时使用 |
| 实现方式 | 两步结构化调用：检查 → 生成（方案 A），不做聊天面板、不做纯模板 |
| 人设定位 | 写 AI 如何认识自己：它是直播里的一个角色，不是主播的助手 |
| 篇幅 | 简短克制；描写过多会让 AI 死板 |
| 内容 | 身份一句、性格关键词、行为方式（≤2 条）、例子（≤2 个） |
| 模型 | 主播已配置的主模型，关闭 thinking |

## 不在本设计内

- 把行为倾向（话多/话少、心里话开关）做成界面开关。
- 把开发者版大肥鱼人设里的接话规则迁入程序默认接话规则（另行处理）。
- 自动改写已有人设；助手只在主播点击时运行。

## 1. 主播看到的流程（「我的 AI」页）

1. 人设编辑框旁新增按钮 **「帮我写人设」**。框里可以是空的、一两句描述，或一段现成的人设，都作为描述输入。
2. **检查**：
   - 信息够：直接进入生成。
   - 缺关键信息：显示最多 3 张问题卡片，每张 2–4 个可点的建议答案，也可自己填写或跳过；主播点「生成」。
3. **预览**：显示人设正文，下方列出「AI 名字/别名」「称呼你」。生成器补写的行为和例子标注「AI 补的」。按钮：「用这个」「重新生成」「取消」。
4. **用这个**：写入草稿（人设、别名、称呼），状态变为「未保存」；仍需主播点「保存人设」，可撤销。沿用现有保存/撤销流程。

追问规则：

- 必问（对应字段已填写则不问）：AI 的名字；AI 怎么称呼主播。
- 仅当描述几乎没有性格信息时（例如只写「可爱」），问一个说话风格问题。
- 其余缺项由生成器按已有描述补全，不追问。
- 跳过名字问题时，生成器按描述取一个名字，标为「AI 补的」，在预览中由主播确认；跳过称呼问题时，人设中用「主播」。
- 主播原文中的具体设定（例如「讨厌香菜」）必须保留，不改成另一个角色。

## 2. 生成的人设

形状（示例：主播输入「傲娇猫娘，爱吐槽，叫我老大」，名字回答「小咪」）：

```
你是小咪，老大的猫娘搭档，正在陪老大直播。
性格：傲娇、爱吐槽。
行为方式：被夸会嘴硬，看不惯就直说。
例子（只体现语气，不要照搬原句）：
- 老大夸你今天很乖 → “哼，本喵一直都很乖好吗。”
- 对面主播说你是假的猫 → “你才是假的，你全家都是假的。”
```

规则：

- 第二人称「你是……」。身份一句：名字、与主播的关系、正在陪播。
- 性格：只用主播给过的词或其直接同义，最多 4 个关键词，不展开描写。
- 行为方式：最多 2 条，每条一句，写性子怎么表现，不写什么时候说话。
- 例子：最多 2 个，格式「场景 → 它会说的一句话」，只示范开口时的语气；固定带「只体现语气，不要照搬原句」。
- 主播原文有的行为和台词优先使用；没有时生成器最多补 1 条行为、2 个例子，并标为补写。
- 不写：何时说话、静默、心里话、字数、输出格式、「必须」「严禁」类规则。

## 3. 程序结构

### Core：`AIVTuber.Core/Persona/PersonaAssistant.cs`

```csharp
internal sealed class PersonaAssistant
{
    Task<PersonaCheckResult> CheckAsync(PersonaDraftInput input, CancellationToken ct);
    Task<PersonaComposeResult> ComposeAsync(PersonaDraftInput input, IReadOnlyList<PersonaAnswer> answers, CancellationToken ct);
}

record PersonaDraftInput(string Description, IReadOnlyList<string> ExistingAiNames, string ExistingStreamerTitle);
record PersonaQuestion(string Id, string Text, IReadOnlyList<string> Suggestions);   // Id: aiName | streamerTitle | style
record PersonaCheckResult(IReadOnlyList<PersonaQuestion> Questions);                 // 空 = 可直接生成
record PersonaAnswer(string QuestionId, string? Text);                               // Text 为 null = 跳过
record PersonaComposeResult(string Persona, IReadOnlyList<string> AiNames, string StreamerTitle, IReadOnlyList<string> Supplemented);
```

- 依赖注入一个 `ILlmClient`（与记忆提取相同：独立 `LlmClient`，主模型，`systemPrompt: ""`），收集流式结果后解析 JSON。
- 两个生成器提示词为程序内置常量，要求只返回 JSON，并写明「只写角色，不写说话规则与格式」。
- 必问规则由程序决定，不交给模型：名字/称呼字段已填就从问题列表中去掉；模型只负责判断风格问题是否需要、以及给出建议答案。

### 结果校验：`PersonaValidator`

拒绝条件（任一）：

- 正文（不含例子里引号内的台词）包含 `PASS`、`【`、`】`、全角括号包裹的格式说明、「字以内」「输出」「必须」「严禁」。
- 行为方式超过 2 条或例子超过 2 个。
- 名字为空，或正文未出现名字；称呼非空时正文未出现称呼。

被拒绝时重试一次（附上拒绝原因）；仍失败则返回错误「没生成好，请改改描述再试」，不写入任何字段。

### 界面

- `StreamerConsoleController` 新增命令 `personaCheck`、`personaCompose`，结果以 `personaAssistant` 消息推回页面。
- `streamer.html` / `streamer.js` / `streamer.css`：按钮、问题卡片、预览区，沿用现有液态玻璃样式。
- 「用这个」只修改草稿：`persona.systemPrompt`、`live.wakeKeywords`、`live.selfName`（均已在主播补丁白名单内）。
- 按钮在云端未授权（未登录、授权失效）时不可用，并显示原因，避免未授权消耗模型额度。

## 4. 出错处理

| 情况 | 表现 |
|---|---|
| 超时（15 秒） | 「AI 没有及时回应，请稍后再试」，草稿不变 |
| 网络/服务错误 | 显示一行可读错误，草稿不变 |
| JSON 解析失败 | 视为一次校验失败，走重试逻辑 |
| 进行中再次点击 | 按钮在进行中禁用；取消会中止请求 |

## 5. 测试

单元测试（假 `ILlmClient`）：

- 缺名字时追问名字；名字和称呼已填时不追问它们。
- 校验拦下含 `【PASS】`、括号心里话格式、「30字以内」的结果，并重试一次。
- 重试仍失败时返回错误，结果中无任何字段改动。
- 「用这个」只改草稿三项，不触发保存。
- 主播原文中的具体设定出现在提示词输入中（不被预处理丢弃）。

真实模型验收（人工）：用 6 条主播描述各跑一次，结果交用户评审，其中包括：空描述、只有「可爱」、「傲娇猫娘，爱吐槽，叫我老大」、一段较长的自由描述、开发者版大肥鱼人设、含具体设定（讨厌香菜、东北口音）的描述。评审关注：是否简短克制、是否像直播里的角色而非助手、是否混入工作流规则。
